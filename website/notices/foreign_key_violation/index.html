Diagnosis

What this notice means

A foreign key references the primary key of another file. A foreign key violation means that the foreign key referenced from a given row (the child file) cannot be found in the corresponding file (the parent file). The Foreign keys are defined in the specification under "Type" for each file.

Operational effect

Why it matters

A row points at an id that does not exist anywhere in the file it references. The reference is dangling, so the record it belongs to cannot be resolved: a trip whose `service_id` is missing from `calendar.txt` never runs, a `stop_times.txt` row whose `stop_id` is missing from `stops.txt` has no location, and a route whose `agency_id` is unknown has no operator. Consumers drop the affected rows, and dropping a `stop_times.txt` row silently removes a stop from a trip. The report names both sides: `childFilename`/`childFieldName` is where the broken reference was written, `parentFilename`/`parentFieldName` is where the id should have been defined, and `fieldValue` is the id that was not found.

Scope

Diagnosis

What usually causes it

  • A typo or case difference in the id — STOP_42 in stop_times.txt against stop_42 in stops.txt. GTFS ids are case-sensitive, and so is this check.
  • A stray space or a zero-width character copied in from a spreadsheet, so the two ids look identical but do not compare equal.
  • A row was deleted from the parent file (a retired stop, a discontinued route) while the rows referencing it were left behind.
  • A partial export: calendar.txt or calendar_dates.txt was regenerated for a new period, and trips still carry service_id values from the old one.
  • Two source systems with different id schemes merged into one feed, so one system's ids never made it into the parent file.
  • An id built by concatenation that lost a prefix or a suffix somewhere in the export pipeline.

Check both sides. Open the parent file named in parentFilename and search for the exact fieldValue from the report. No match means the id was never defined; a match that differs only in case or whitespace means the child row needs normalising, not a new parent row.

Repair

How to fix it

Decide which side is wrong before editing anything. If the id in the child row is a typo or a leftover from an older export, correct it to an id that exists in the parent file. If the id is right and the parent row is genuinely missing, add that row to the parent file with its real data.

  1. 1
    Locate the record

    Open the child file named in the report (stop_times.txt, trips.txt, routes.txt …) and use the report fields below to find the exact row.

  2. 2
    Change the source data

    Apply the repair described above to that record, and leave unrelated rows alone.

  3. 3
    Validate again

    Rebuild the GTFS archive and confirm that foreign_key_violation no longer appears for the record.

Do not do this: Do not invent a placeholder row in the parent file just to make the notice go away. A fabricated stops.txt entry at 0,0 for a missing stop_id turns a loud error into a stop in the Gulf of Guinea that riders will be routed to, and a fake calendar.txt service with every day set to 0 turns a broken trip into a trip that quietly never runs. Add the real record, or remove the reference.

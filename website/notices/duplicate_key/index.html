Diagnosis

What this notice means

The values of the given key and rows are duplicates.

Operational effect

Why it matters

Two rows share the value that is supposed to identify a row uniquely, so every reference to that id is ambiguous. Consumers resolve it by keeping one row and discarding the other, and which one survives is not defined — a duplicated `stop_id` can quietly relocate a stop, and a duplicated `trip_id` can drop half a schedule.

Scope

Affected files and report fields

The affected file is determined at validation time. Use the filename or related context field in your report to locate it.

Diagnosis

What usually causes it

  • The same source file exported or appended twice, so every row appears in duplicate.
  • Two agencies or depots merged into one feed while each kept its own id numbering.
  • stop_sequence restarted at 1 partway through a trip, or repeated a value, so the trip_id + stop_sequence pair collides.
  • An id reused after a record was retired, so a new stop inherited a decommissioned stop's stop_id.
  • A spreadsheet autofilled an id column down a block of rows.

Repair

How to fix it

Give each record its own id, or delete the row that is a genuine duplicate. For composite keys such as `stop_times.txt` (`trip_id` + `stop_sequence`) or `calendar_dates.txt` (`service_id` + `date`), it is the combination that has to be unique, so renumbering the sequence is often the correct repair rather than renaming anything.

  1. 1
    Locate the record

    Open the file named in the report (stops.txt, trips.txt, stop_times.txt …) and use the report fields below to find the exact row.

  2. 2
    Change the source data

    Apply the repair described above to that record, and leave unrelated rows alone.

  3. 3
    Validate again

    Rebuild the GTFS archive and confirm that duplicate_key no longer appears for the record.

Do not do this: Do not fix a duplicated id by appending _2 to one of the rows without checking what references it. If both rows are really the same entity, half your stop_times.txt now points at an id nobody defines and a foreign_key_violation takes the error's place.
